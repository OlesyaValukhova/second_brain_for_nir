# Правила работы агента с исследовательским vault

## Главное

Эта папка (`vault/`) — единственная рабочая база Obsidian для исследования. Изменения заметок вносятся только здесь.

Не использовать как параллельные рабочие базы:

- `../research/` — сохранённый источник для сверки и переноса уникальных материалов;
- `../../nir-digital-urbanism/Исследование/` — прежняя локальная копия, оставленная как страховка.

Нельзя массово копировать, удалять или перезаписывать заметки между этими папками без явного запроса пользователя и предварительной сверки.

## Как работать с заметками

- Сохранять принцип «одна сущность — одна заметка».
- Добавлять связи выборочно: между вопросом, методом, источником, экспериментом и выводом. Не связывать все заметки со всеми.
- Сохранять историю в `08 Архив/`; архив не использовать как источник актуальных решений без проверки.
- Перед изменением исследовательских вопросов, гипотез, методики, протоколов экспериментов или текста работы запросить явное разрешение пользователя.
- После добавления или переноса заметок проверять внутренние ссылки и отсутствие случайных дублей.

## Совместная работа с картой проблемы

Карта [[02 Литература/00 Карта проблемы. Автомобильное сопровождение.canvas]] — рабочая схема рассуждения, а не автоматический граф всех заметок. Её цель — помогать человеку видеть логику исследования; подробности и источники остаются в связанных карточках.

Рабочий цикл:

1. Пользователь формулирует следующий вопрос в логике исследования: о проблеме, её условиях, истории, процессах, нормах или известных способах решения.
2. Агент сначала ищет ответ в vault. Если данных недостаточно, проводит внешнюю проверку по первоисточникам и явно отделяет подтверждённое от предположений.
3. Для каждого нового устойчивого вывода создаёт отдельную заметку-карточку: один конкретный тезис, краткое человеческое название, пояснение, ссылки на источники и границы вывода. Не дублировать заголовок внутри текста карточки.
4. Новые карточки добавляются в существующую Canvas-карту только по запросу пользователя или когда он явно просит обновить схему. Не создавать параллельную схему без такого запроса.
5. Связи на Canvas должны выражать смысл: «объясняет», «задаёт условия», «подтверждает», «ограничивает», «размещает сеть» и т. п. Не использовать линейную цепочку, если явная последовательность не подтверждена; не соединять карточки ради полноты.
6. Перед сохранением Canvas агент проверяет: JSON читается, все пути к файлам существуют, идентификаторы и связи не дублируются, карточки не накладываются. При чтении и записи Canvas в PowerShell использовать UTF-8.

Оформление Canvas:

- центральные вопросы и узлы размещать как точки ветвления, а не как контейнеры для всего содержания;
- группировать карточки по типу аргумента цветом, сохраняя принятую в карте палитру;
- оставлять между карточками свободное пространство и вести линии так, чтобы их можно было прочесть;
- связывать с главной карточкой только основные ветви; свидетельства подключать к соответствующему тезису;
- если пользователь просит изменить раскладку или связи, не удалять сами заметки, пока он прямо не попросит об этом.

## Протокол использования доказательств

Граф Obsidian — это навигация, а не подтверждение, что агент прочитал релевантные источники. Перед работой над методикой, экспериментом, интерпретацией или текстом вывода агент обязан открыть [[00 Карта решений и доказательств]]. Затем он читает заметки из строки карты, соответствующей задаче.

Для работы, которая развивает аргументацию ВКР, агент также открывает [[00 Каркас ВКР/00. Содержание и логика ВКР]] и релевантную содержательную карточку тезиса.

Для теоретического обзора агент начинает с [[02 Литература/Схема. Детальная карта свидетельств литературы]], затем открывает строку с нужным источником, релевантную карточку из `02 Литература/Теоретические тезисы/` и исходный реестр. Краткая схема служит только оглавлением. Атомарная карточка не заменяет первоисточник или реестр: она задаёт вопрос и границу вывода.

Если работа развивает уже начатую линию литературы, агент сначала открывает её Canvas-карту (например, [[02 Литература/00 Карта проблемы. Автомобильное сопровождение.canvas]]). Новый источник добавляется на эту карту отдельной карточкой с конкретным результатом и стрелкой «подтверждает», «ограничивает», «противоречит» или «даёт альтернативу». Не создавать для него новую независимую схему, пока пользователь явно не попросит отделить тему.

В результате агент обязан разделить:

- что подтверждено конкретными заметками vault (перечислить их);
- что является рабочим предположением;
- что требует внешней проверки и отсутствует в vault.

Нельзя заменять уже сохранённые доказательства общими знаниями модели или выдавать предположение за вывод из статьи. Если в карте нет маршрута для задачи, агент фиксирует пробел в `06 План и журнал/00-defect-registry.md` либо запрашивает направление пользователя.

## Режим исследовательской задачи

Для сложной задачи агент создаёт копию [[Шаблон исследовательской задачи]] в `06 План и журнал/` и проходит роли из шаблона: координатор → исследователь литературы → методолог → исполнитель эксперимента → независимый рецензент. Это облегчённый процесс, вдохновлённый CoResearchGraph: он не запускает внешний сервис и не создаёт вторую базу данных.

До принятия содержательного вывода агент показывает пользователю итог по трём полям: «подтверждено в vault», «рабочие предположения», «требует внешней проверки». Вопросы, гипотезы, метод, протокол эксперимента и текст ВКР изменяются только после явного подтверждения пользователя.

## Git-синхронизация

GitHub не синхронизирует изменения сам по себе.

Перед началом содержательной работы:

1. Проверить состояние репозитория.
2. Получить изменения из GitHub (`git pull`).

После завершения содержательной работы:

1. Проверить список изменённых файлов.
2. Сообщить пользователю, какие файлы изменены, чтобы он мог зафиксировать их через GitHub Desktop.

Коммит и отправка в GitHub выполняются агентом только по явному запросу пользователя.

Не выполнять `push --force`, `reset --hard`, массовое удаление или автоматическое разрешение конфликтов без явного разрешения пользователя.

Если обнаружены изменения с другого устройства или конфликт, остановиться, показать пользователю затронутые файлы и предложить безопасный способ объединения.
